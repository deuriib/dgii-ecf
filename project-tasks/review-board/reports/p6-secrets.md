# Secrets & Credential Hygiene Review

**Scope:** `deuriib/dgii-ecf` @ `8b7879a` — two published SDKs (`@deuriib/dgii-ecf`, `py-dgii-ecf`) for
DGII e-CF electronic invoicing.
**Auditor role:** Secrets & credential hygiene (detection, handling, rotation, leak response).
**Method:** every finding is marked **verified by running** or **verified by reading**. All throwaway
material (`.p12`, PEM keys, fake passphrases, fake bearer token) was generated by me under `/tmp` and
never written into the repo. No real secret appears in this report — where a real value exists I give
`file:line` plus at most the first 4 characters.

---

## Verdict

**Conditional pass on detection, fail on handling, fail on leak response.**

The repo does the hard part right: **there are no long-lived publish tokens to steal.** Both publish
jobs use OIDC trusted publishing (`python.yml:65-69`, `typescript.yml:70-74`) — no `NPM_TOKEN`, no
`PYPI_TOKEN`, nothing to exfiltrate from a build log. Git history is clean across 150 commits
(verified by running `gitleaks git`). That is a genuinely good posture and most repos do not have it.

Three things are wrong, in order of how much they'd hurt:

1. **Detection cannot see history, and CONTRIBUTING claims it can.** The `gitleaks` hook is
   `gitleaks dir .` (`.pre-commit-config.yaml:85`) — working tree only. CI runs the same hook
   (`pre-commit.yml:49`), with `actions/checkout` at default depth 1. A secret committed and later
   deleted is invisible to every gate in this repo, while `CONTRIBUTING.md:101` tells contributors
   "a commit made with `--no-verify` is still verified before merge." I demonstrated the gap:
   a committed-then-deleted passphrase was found by `gitleaks git` and missed by `gitleaks dir`.
2. **The private key and passphrase print themselves.** TS `P12Reader` keeps `passphrase` as a plain
   runtime-visible property, so `console.log(reader)` prints the passphrase (`certificate.ts:25`).
   Python `P12ReaderData` is a `slots` dataclass, so its auto-generated `repr` prints the PEM private
   key (`certificate.py:20-26`). Both `ECF` clients retain the key material as a plain attribute
   (`client.ts:186`, `client.py:166`), so `JSON.stringify(ecf)` dumps the signing key. All verified by
   running. Any `console.log`, `logger.debug`, Sentry breadcrumb, or framework exception dump that
   touches these objects is a full private-key disclosure.
3. **There is no 3 a.m. runbook.** `SECURITY.md` says "Rotate immediately if exposed" (line 32) and
   stops. No DGII-side revocation path, no CI-secret rotation list, no history purge, no audit step.
   For a `.p12` that is the whole game: rotating at the *provider* means DGII revoking the certificate
   and checking what was issued with it. Deleting the file from the repo accomplishes nothing.

A PR cannot reach the npm/PyPI credential — the publish `if:` guards are correct and
`pull_request_target` is used nowhere. The realistic path to a publish instead runs through
`release-please.yml`, which grants `contents: write` + `actions: write` to an action pinned at the
mutable tag `googleapis/release-please-action@v5`.

## Detection test results

All tests run against throwaway material I generated in `/tmp/p6scratch` and `/tmp/p6repo-<pid>`,
using the repo's own `.gitleaks.toml` and `.pre-commit-config.yaml` verbatim.

| **`cert.p12.b64`** — base64 of the keystore | ❌ regex miss | ❌ **no rule matches** | **NO — full miss** |
| Committed in commit 1, deleted in commit 2 | n/a (not in tree) | ❌ not in tree | **NO — full miss** |

Two things this table says that are worth stating plainly:

**The two gates are genuinely complementary, and the belt-and-suspenders design works.** The
extension regex misses `id_rsa`, and gitleaks catches it because it is a content rule, not a name
rule. A `.p12` renamed `identity.bin` would fail the regex and gitleaks would still flag it. That is
the correct layering and it is not accidental.

**Two full misses.** (a) A **base64-encoded `.p12`** — which is precisely the representation
`DGII_P12_BASE64` uses in CI (`integration.yml:66`) — passes every gate. A developer pasting the
CI secret's value into a fixture, a doc example, or a debug script would not be stopped. (b) A secret
that was committed and then deleted is invisible forever (F-SECRET-04).

### Allowlist review

`.gitleaks.toml` is one `[extend] useDefault = true` plus a single path allowlist:

```toml
[[allowlists]]
description = "Signing artifacts written by the example scripts."
paths = ['''^examples/output/''']
```

I checked this for entries that could hide a real secret. **There are none.** The allowlist is a
single anchored path prefix, it has no `regexes` or `stopwords` escape hatch, and `^examples/output/`
cannot match a tracked source file. It is also benign for a second reason: `examples/output/` is
gitignored (`.gitignore:206`), so the path cannot reach a commit anyway. The allowlist is redundant
rather than dangerous — the one thing `[extend] useDefault` without a broader allowlist gets right is
that precision stays high, which is what keeps a scanner trusted. **No finding.** Contrast with the
usual failure mode (an allowlist entry for `test/` or `fixtures/` that silently mutes the entire test
tree) — this config avoids it.

**History in CI:** not scanned. `grep -rn gitleaks .github/` returns nothing — the only gitleaks in CI
is via `mise run hooks` (`pre-commit.yml:49`), which is the working-tree `dir` command. No
`fetch-depth: 0` appears in any workflow, so a history scan would not have the commits to scan even if
added to the current job. `gitleaks git` on the real repo: **150 commits scanned, no leaks** — the
history is clean today.

## Findings

### F-SECRET-01 — TS `P12Reader` exposes the `.p12` passphrase as a runtime property

- **Severity:** High
- **Verified by running**
- **Where:** `packages/typescript/src/certificate.ts:25`
  (`constructor(private readonly passphrase: string) {}`)
- **What leaks:** TypeScript's `private` is erased at compile time. At runtime `passphrase` is an
  ordinary own property, enumerable and stringified. Demonstrated:

  ```
  util.inspect(reader)  → P12Reader { passphrase: 'throwaway-passphrase-p6' }
  JSON.stringify(reader) → {"passphrase":"throwaway-passphrase-p6"}
  Object.keys(reader)    → [ "passphrase" ]
  ```
- **Blast radius:** C2. Combined with C1 (which is one `getKeyFromFile` call away and also lands in a
  plain object), a single `console.log(credentials)` or a framework that serialises constructor
  arguments — NestJS request logging, a Sentry breadcrumb with `extra: { reader }`, an error reporter
  that walks `cause` and plain objects — discloses both halves of the signing identity in cleartext.
  The passphrase is the *only* thing protecting the `.p12` if the file itself leaks later.
- **Fix:** Do not keep the passphrase on the instance. Either pass it through to `load()` and drop the
  reference, or make it non-enumerable and define an explicit redacted `toJSON`/`inspect.custom`:

  ```ts
  export class P12Reader {
    #passphrase: string;                       // true private field, not erased
    constructor(passphrase: string) {
      this.#passphrase = passphrase;
      Object.defineProperty(this, 'passphrase', { value: undefined, enumerable: false });
    }
    [util.inspect.custom](): string { return 'P12Reader(<redacted>)'; }
    toJSON(): string { return 'P12Reader(<redacted>)'; }
  }
  ```
  `#private` is the load-bearing part; the `inspect`/`toJSON` overrides are the belt.
- **Verification:** `bun run /tmp/check.ts` with
  `util.inspect(new P12Reader('x')).includes('x') === false` and
  `JSON.stringify(new P12Reader('x')).includes('x') === false`. Add it to
  `packages/typescript/test/certificate.test.ts` so it cannot regress.

### F-SECRET-02 — Python `P12ReaderData` `repr` prints the PEM private key; both `ECF` clients retain it

- **Severity:** High
- **Verified by running**
- **Where:**
  - `packages/python/src/py_dgii_ecf/certificate.py:20-26` — `@dataclass(frozen=True, slots=True)`
    with `key: str | None = None` and no `repr=False`
  - `packages/python/src/py_dgii_ecf/certificate.py:101-105` — the key is placed in that field
  - `packages/python/src/py_dgii_ecf/client.py:166` — `self._credentials = credentials`
  - `packages/typescript/src/client.ts:186` — `this.credentials = credentials`
- **What leaks:** the auto-generated dataclass `repr`. Demonstrated:

  ```
  repr(data)            → P12ReaderData(key='<PEM-PRIVATE-KEY>\nMIIEvAIBADAN… (3437 chars)
  'PRIVATE KEY' in str(data)              → True
  'PRIVATE KEY' in str(asdict(data))      → True
  'PRIVATE KEY' in f"{data}"              → True
  'PRIVATE KEY' in util.inspect(tsEcf, {depth:3}) → True
  'PRIVATE KEY' in JSON.stringify(tsEcf)          → True
  ```
  and on the TS side the flat result object carries the same material:
  `Object.keys(data) → [ "key", "cert", "publicKey" ]`, both `util.inspect` and `JSON.stringify` print
  `<PEM-RSA-PRIVATE-KEY>`.
- **Blast radius:** C1. Uvicorn/FastAPI/django exception dumps, `logging.exception(err)` where `err`
  holds a `DgiiError` whose `cause` chain reaches a `P12ReaderData`, `pprint` in a notebook,
  `dataclasses.asdict` written to a debug endpoint, a Celery task result payload that pickles and logs
  the argument. Because `ECF` holds `_credentials` for the entire client lifetime, `vars(ecf)` — which
  is exactly what a debugging session or `pytest --showlocals` failure produces — dumps the signing
  key alongside the environment. This is not theoretical: `pytest` prints local variables on
  assertion failure, so **one failing integration test can print the production signing key into a CI
  log.** `integration.yml:79` runs `uv run pytest tests/integration -v` with the real `.p12` loaded.
- **Fix:** mark the sensitive fields out of `repr` and give the type an explicit safe representation:

  ```python
  @dataclass(frozen=True, slots=True)
  class P12ReaderData:
      key: str | None = field(default=None, repr=False)
      cert: str | None = None
      public_key: str | None = None

      def __repr__(self) -> str:
          return f"P12ReaderData(cert={self.cert!r}, key=<redacted>)"
  ```
  Do the same for `AuthToken.token` (F-SECRET-03). On the TS side define
  `toJSON()`/`[util.inspect.custom]()` on the returned object (or a small `P12ReaderData` class that
  produces it) returning `{ cert, publicKey, key: '<redacted>' }`.
- **Verification:**
  `uv run pytest -q -k "repr and not private_key"` — add an assertion
  `assert "PRIVATE KEY" not in repr(reader.get_key_from_file(p12).unwrap())`. Also
  `assert "PRIVATE KEY" not in str(vars(ecf))`.

### F-SECRET-03 — `py_dgii_ecf authenticate` prints the bearer token; `AuthToken` repr includes it

- **Severity:** Medium
- **Verified by running** (`AuthToken`) / **verified by reading** (`cli.py`)
- **Where:**
  - `packages/python/src/py_dgii_ecf/cli.py:87` — docstring: *"Authenticate against DGII and print the
    access token."*
  - `packages/python/src/py_dgii_ecf/cli.py:95` — `typer.echo(f"token: {token.token}")`
  - `packages/python/src/py_dgii_ecf/types.py:48-53` — `@dataclass(frozen=True, slots=True) class
    AuthToken` with `token: str`, no `repr=False`
- **What leaks:** the raw bearer token, verbatim, to stdout. Demonstrated:
  `'SECRET-BEARER-MARKER' in repr(AuthToken(...))` → `True`; same for `str()`.
- **Redaction audit — the rest is clean.** I traced every error path and stringification and the
  token is *not* redacted anywhere it isn't supposed to be, and *is* correctly absent everywhere it
  matters:
  - `http.py:143-154` `_headers()` builds `Authorization: Bearer …` per request; there is no cached
    header object, so `clear_token()` (`http.py:139-141`) genuinely drops it — no stale-token replay.
  - `HttpClient.__repr__` is the default object repr → does not print `_token`. Verified by running.
  - `_parse()` (`http.py:156-181`) puts the *response* body in `DgiiError.data`, never the request
    headers. No request-header echo anywhere.
  - `DgiiError.__str__` returns `self.message` only (`errors.py:194-195`); the token never enters a
    message. The `Cause` chain from `httpx2.HTTPError` does not carry headers.
  - TS side: `http.ts:132,141,155-164,196-197` mirrors this correctly; `token` is a private property
    but the class has no custom `inspect`/`toJSON`, and the *class instance* default repr is safe.
  - The only token exposure is the deliberate CLI `echo` and the `AuthToken` repr.
- **Blast radius:** C3 — bounded, because DGII tokens expire. But a token printed to stdout lands in
  terminal scrollback, a `tee`'d log, a CI job log, a shared screen, and any shell wrapper the user
  wrote. `cli.py:95` is one command away from `authenticate > token.txt`.
- **Fix:** print a fingerprint instead of the value — enough to confirm auth worked, useless to an
  attacker:

  ```python
  fp = hashlib.sha256(token.token.encode()).hexdigest()[:12]
  typer.echo(f"token: <redacted sha256:{fp}>")
  typer.echo(f"expira: {token.expira}")
  ```
  and add `field(repr=False)` to `AuthToken.token`. If a caller genuinely needs the raw value, add
  `--show-token` behind an explicit flag so it is a deliberate act, not the default.
- **Verification:** `py-dgii-ecf authenticate … 2>&1 | grep -c '<redacted>'` ≥ 1 and
  `… | grep -Ec '^[A-Za-z0-9_-]{40,}\.'` = 0.

### F-SECRET-04 — `gitleaks` scans the working tree only; history is never scanned, and CONTRIBUTING says it is

- **Severity:** High
- **Verified by running**
- **Where:**
  - `.pre-commit-config.yaml:85` — `entry: gitleaks dir . --redact --no-banner`
  - `.github/workflows/pre-commit.yml:49` — `run: mise run hooks` → `pre-commit run --all-files` → the
    same `dir` command
  - `.github/workflows/pre-commit.yml:21` — `uses: actions/checkout@v7`, no `fetch-depth`
  - `CONTRIBUTING.md:100-101` — *"a commit made with `--no-verify` is still verified before merge"*
- **What fails to be caught:** any secret that entered a commit and was later removed. Demonstrated
  in a scratch repo: committed `DGII_P12_PASSWORD=…` in commit 1, `git rm` in commit 2.
  `gitleaks dir .` → found the 8 unrelated current-tree files, **did not** report the deleted one.
  `gitleaks git .` → reported `hist/.env-real` immediately. Nothing in this repo ever runs
  `gitleaks git`.
- **Blast radius:** C1, C2, C4, C7. This is the single most consequential gap because it inverts the
  correct mental model. The most common leak response is "commit that deletes the secret" — after
  which this repo's gates are green, the PR merges, and everyone believes it is resolved. The
  credential is still live at the provider and still in every clone, fork, and the reflog.
  `CONTRIBUTING.md:101` actively reinforces the false belief by promising `--no-verify` is caught —
  true for the tree, false for the leak that actually matters. Note also that `--all-files` only sees
  git-tracked paths, so a gitignored `.p12` sitting in the worktree is not scanned either (correct,
  but worth knowing before trusting the gate).
- **Fix:** add a history scan and stop relying on the tree scan for the history question.

  ```yaml
  # .github/workflows/secret-scan.yml
  name: secret-scan
  on: [push, pull_request]
  permissions:
    contents: read
  jobs:
    gitleaks:
      runs-on: ubuntu-24.04
      steps:
        - uses: actions/checkout@<sha>
          with:
            fetch-depth: 0                 # REQUIRED: full history for `gitleaks git`
        - run: mise install && mise exec -- gitleaks git . --redact --no-banner
  ```
  Keep the pre-commit `dir` hook as the fast local gate — it is doing its job — and parallelise it in
  CI with something like `gitleaks git . --log-opts="--all"` so a leak on any branch is caught. Then
  correct `CONTRIBUTING.md:100-101` to say what is actually true.
- **Verification:** the scratch-repo repro above is the test. In the real repo:
  `git commit --allow-empty -m tmp && git log --all | wc -l` then
  `gitleaks git . --log-opts="--all"` must scan the full 150 commits (it does today: "150 commits
  scanned … no leaks found") — and CI must be the thing running it.

### F-SECRET-05 — A base64-encoded keystore passes every detection gate

- **Severity:** Medium
- **Verified by running**
- **Where:** `.pre-commit-config.yaml:94` (extension regex), `.gitleaks.toml` (no base64-PKCS#12 rule)
- **What fails to be caught:** `cert.p12.b64` — `base64 -w0 identity.p12` — is not matched by the
  `\.(p12|pfx|…)$` regex (wrong extension) and matches no gitleaks rule. It is the *exact* form the CI
  secret holds (`DGII_P12_BASE64`, `integration.yml:32,66,112`), so it is the form most likely to be
  copy-pasted from the secret store into a "temporary" test fixture or a debugging script.
- **Blast radius:** C1. Blast radius is identical to a raw `.p12`, and unlike a raw `.p12` nothing
  stops it.
- **Fix:** add a rule that catches a base64 PKCS#12 by its structural prefix rather than by filename.
  A base64 DER `SEQUENCE` starting `30 82 …` encodes to `MII…`; a PFX begins with the
  `pkcs-12` OID. Add to `.gitleaks.toml`:

  ```toml
  [[rules]]
  id = "base64-pkcs12"
  description = "Base64-encoded PKCS#12 keystore"
  regex = '''(?i)(?:MII[A-Za-z0-9+/]{200,})'''
  entropy = 5.0
  keywords = ["MII"]
  ```
  Tune against `.p12` fixtures so precision holds — the whole value of this gate is that developers
  do not learn to bypass it. Extend the `certificate-material` regex to
  `\.(p12|pfx|pem|jks|jceks|keystore|der|p8|p12\.b64|pfx\.b64|p12\.base64|b64)$` as the cheap half.
- **Verification:** `base64 -w0 /tmp/x.p12 > /tmp/cert.p12.b64 && gitleaks dir /tmp --config
  .gitleaks.toml` must return exit 1 and one `base64-pkcs12` finding.

### F-SECRET-06 — `release-please.yml` grants `contents: write` + `actions: write` to a mutable-tag action

- **Severity:** High
- **Verified by reading**
- **Where:**
  - `.github/workflows/release-please.yml:8-13` — `contents: write`, `pull-requests: write`,
    `issues: write`, **`actions: write`**
  - `.github/workflows/release-please.yml:20` — `uses: googleapis/release-please-action@v5`
  - `.github/workflows/release-please.yml:30-37,39-46` — `gh workflow run … --ref <tag>` with
    `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`
- **What leaks:** not a token value — the *authority*. `@v5` is a mutable tag. Every action in this
  repo is pinned to a mutable major tag; **zero** are pinned to a commit SHA
  (`actions/checkout@v7`, `astral-sh/setup-uv@v7`, `oven-sh/setup-bun@v2`, `jdx/mise-action@v5`,
  `actions/cache@v6`, `actions/configure-pages@v6`, `actions/upload-pages-artifact@v5`,
  `actions/deploy-pages@v5`, `crazy-max/ghaction-github-labeler@v6`). If any of those tags is moved —
  by a compromised maintainer account, a stolen release credential, or a supply-chain attack on the
  action itself — the moving code runs with this workflow's token. For `release-please.yml` that token
  can push commits and tags to `main` (`contents: write`) *and* dispatch arbitrary workflows
  (`actions: write`), which is the documented path to a publish (`release-please.yml:30-37`).
- **Blast radius:** C5 and C6 — the publish authority is OIDC-federated and tokenless, so the *only*
  way to reach it is to control the ref a publish workflow runs on. `contents: write` plus
  `actions: write` in a single job is exactly that control. This is the realistic "compromised code
  reaches the npm/PyPI token" path in this repo, and it is a supply-chain compromise of the published
  SDK, not just the repo.
- **Fix:** pin every `uses:` to a full 40-char commit SHA with the version in a comment, and let
  Dependabot's `github-actions` ecosystem keep them current:

  ```yaml
  - uses: googleapis/release-please-action@<40-char-sha>  # v5.0.0
  ```
  Then split the job: keep `contents: write` + `pull-requests: write` on the release-please step and
  move the two `gh workflow run` steps into a separate job with **only** `actions: write` (not
  `contents: write`). A token that can dispatch a publish has no business also being able to push.
  Consider a protected `environment: release` with required reviewers on the publish jobs.
- **Verification:** `grep -rhn "uses:" .github/workflows/ | grep -vE '@[0-9a-f]{40}' | grep -v '^#'`
  must return nothing. Add `.github/dependabot.yml` with a `github-actions` entry so the pins do not
  go stale.

### F-SECRET-07 — `docs.yml` gives `id-token: write` and `pages: write` to a PR-triggered job

- **Severity:** Medium
- **Verified by reading**
- **Where:**
  - `.github/workflows/docs.yml:17-20` — workflow-level `permissions:` with `pages: write` and
    **`id-token: write`**
  - `.github/workflows/docs.yml:10-14` — the workflow triggers on `pull_request`
  - `.github/workflows/docs.yml:36` — `mkdocs build --strict` (executes PR-controlled `mkdocs.yml`,
    including any `hooks:`/plugin config)
- **What leaks:** OIDC minting authority inside a job that runs untrusted PR content. Workflow-level
  `permissions:` apply to *every* job, so the `build` job — the one that runs on `pull_request` and
  executes `mkdocs.yml` from the PR — inherits `id-token: write` and `pages: write`. Only the `deploy`
  job needs them, and only on `main` (`docs.yml:52` already gates it correctly).
- **Blast radius:** indirect. npm/PyPI trusted publishing binds the OIDC subject to the release
  workflow and ref, so a `refs/pull/N/merge` token is very unlikely to be exchangeable for a publish
  token — I could not construct that exchange. The real exposures are: (a) any downstream OIDC trust
  policy that keys on *repository* rather than *workflow+ref* is reachable from a PR; (b) Pages
  artifact poisoning toward the `github-pages` environment; (c) it violates least privilege in the one
  job that runs attacker-influenced code.
- **Fix:** move the permissions onto the job that needs them and leave the workflow default read-only:

  ```yaml
  permissions:
    contents: read            # workflow default, inherited by build
  jobs:
    build:
      permissions:
        contents: read
        # NO id-token, NO pages:write
    deploy:
      permissions:
        pages: write
        id-token: write       # only here, only on main
  ```
  Also add `environment: github-pages` required-reviewer protection if Pages content is trusted.
- **Verification:** `mkdocs build` in a PR fork and confirm the job cannot call
  `core.getIDToken()`; or inspect the rendered job's effective permissions with
  `gh api repos/{owner}/{repo}/actions/runs/{run_id}/jobs` and assert `id-token` is absent on `build`.

### F-SECRET-08 — npm publish is not gated by a protected `environment:`; PyPI is

- **Severity:** Medium
- **Verified by reading**
- **Where:** `.github/workflows/typescript.yml:65-74` (no `environment:`) vs
  `.github/workflows/python.yml:62-64` (`environment: name: pypi`)
- **What leaks:** nothing directly — this is a missing human gate. The two publish jobs are
  asymmetric. `python.yml` routes through the `pypi` environment, which can carry required reviewers
  and environment-scoped secrets. `typescript.yml` publishes to npm with no environment at all, so the
  moment a `typescript-v*` tag exists and CI is green, `npm publish --access public`
  (`typescript.yml:101`) runs unattended.
- **Blast radius:** C5. `@deuriib/dgii-ecf` signs tax documents in its users' name. An unreviewed
  publish is a supply-chain event with legal consequences for downstream taxpayers, and the OIDC
  trusted-publisher binding does not distinguish "a human meant this" from "release-please tagged it".
- **Fix:** add `environment: { name: npm, url: https://www.npmjs.com/package/@deuriib/dgii-ecf }` to
  the `publish` job and configure required reviewers on that environment, matching PyPI. Register the
  `npm` environment as the trusted publisher in the npm package settings so OIDC is scoped to it.
- **Verification:** `gh api repos/{owner}/{repo}/environments` lists both `npm` and `pypi`; a publish
  run pauses at the environment with `waiting` status.

### F-SECRET-09 — Integration workflow leaves the decoded keystore at a predictable path; `shred` is not a guarantee

- **Severity:** Low
- **Verified by reading**
- **Where:**
  - `.github/workflows/integration.yml:64-69` and `:110-115` —
    `printf '%s' "$P12_BASE64" | base64 -d > "$RUNNER_TEMP/identity.p12"` then `chmod 600`
  - `.github/workflows/integration.yml:81-84` and `:127-130` — `shred -u … || rm -f …`
- **What leaks:** the plaintext keystore on a GitHub-hosted runner for the duration of the job. The
  path `$RUNNER_TEMP/identity.p12` is fixed and predictable, so any step (including a compromised
  dependency running during `uv sync`, `bun install`, or the test suite itself) can read it by path.
  `shred` is also ineffective against copy-on-write/overlay filesystems, which is what GitHub runners
  use — the `|| rm -f` fallback makes that explicit.
- **Blast radius:** C1. Contained to the runner's lifetime and to GitHub-hosted (ephemeral, single-tenant)
  machines, which is why this is Low and not High. It would be High on a self-hosted runner.
- **Fix:** (a) the `chmod 600` + `$RUNNER_TEMP` choice is already the right shape — keep it; (b) put
  the file at an unpredictable name (`identity-$(openssl rand -hex 8).p12`) so path-guessing fails;
  (c) prefer reading the base64 directly into the SDK (`getKeyFromStringBase64` /
  `get_key_from_base64`, which both packages already expose) rather than materialising a file at all;
  (d) treat `shred` as best-effort hygiene, not a control — rely on runner ephemerality for the actual
  guarantee, and do not reuse this pattern on self-hosted runners.
- **Verification:** grep the job log for `identity.p12` and confirm it appears only in the decode and
  cleanup steps; assert no test writes it to a repo path.

### F-SECRET-10 — `.gitignore` and the `certificate-material` regex do not cover the same extensions

- **Severity:** Low
- **Verified by reading**
- **Where:** `.gitignore:189-192` (`*.p12 *.pfx *.pem *.key *.crt *.cer`) vs
  `.pre-commit-config.yaml:94` (`p12|pfx|pem|jks|jceks|keystore|der|p8`)
- **What leaks:** nothing by itself — it is a defence-in-depth inconsistency. `*.p8`, `*.jks`,
  `*.jceks`, `*.keystore` and `*.der` are rejected by the hook but **not** gitignored, so they show up
  as untracked files in `git status` (inviting `git add -A`) and are one careless commit away from the
  tree. Conversely `*.crt` and `*.cer` are gitignored but not hook-rejected — those are public
  certificates, so that direction is harmless. `id_rsa` (no extension) is covered by neither;
  gitleaks' content rule is the only thing catching it, which the test results confirm it does.
- **Blast radius:** C1 — low probability, and gitleaks is the real backstop.
- **Fix:** make `.gitignore` a superset of the hook regex:
  `*.p8 *.jks *.jceks *.keystore *.der id_rsa id_ecdsa id_ed25519 *.b64`. Keep the hook regex as-is.
- **Verification:** for each extension in the hook regex, `git check-ignore -q "x.$ext"` must exit 0.

### F-SECRET-11 — `examples/python/generate_cert.py` takes the passphrase from `argv`

- **Severity:** Low
- **Verified by reading**
- **Where:** `examples/python/generate_cert.py:20` — `password = sys.argv[2] if len(sys.argv) > 2 else "test"`
- **What leaks:** the passphrase appears in `ps`/`/proc/<pid>/cmdline` and in shell history. The
  default is `"test"` and this script generates a *throwaway* cert, so the exposure is genuinely
  minor. It is a finding only because examples are how people learn: the SDK's own CLI does this
  correctly (`cli.py:30`, `typer.Option(prompt=True, hide_input=True)` — a hidden prompt, not a flag)
  and the examples then model the opposite.
- **Blast radius:** C2 — none today (throwaway cert), but it teaches the wrong pattern for a script a
  user might adapt for a real keystore.
- **Fix:** match the CLI — `getpass.getpass()` or an env var — and have the script print the path it
  wrote rather than accepting a passphrase argument. Apply the same to
  `examples/typescript/generate-cert.ts` if it takes a flag.
- **Verification:** `grep -rn "argv\[2\]\|process.argv" examples/ | grep -i pass` returns nothing.

### F-SECRET-12 — `SECURITY.md` and `CONTRIBUTING.md` make a detection claim the pipeline does not back

- **Severity:** Medium (documentation × consequence — it is what makes F-SECRET-04 dangerous)
- **Verified by reading**
- **Where:**
  - `CONTRIBUTING.md:99-101` — *"The hooks are not a substitute for CI: the `pre-commit` workflow runs
    `mise run hooks` on every pull request, so a commit made with `--no-verify` is still verified
    before merge."*
  - `CONTRIBUTING.md:107` — *"`gitleaks` scans every file"* (true of the tree, silent on history)
  - `AGENTS.md:107-108` — *"`.p12`, `.pem`, keys and tokens never enter the repo: the
    `certificate-material` hook and `gitleaks` reject them."*
- **What fails:** the claim is true and simultaneously misleading. "Verified before merge" is true for
  the *current tree*; it is false for the leak that matters (commit-then-delete), which this pipeline
  cannot see. A contributor who reads `CONTRIBUTING.md:101` concludes they are covered by CI and has
  no reason to run `filter-repo` after realising they committed a passphrase.
- **Blast radius:** C1, C2 — it converts a technical gap (F-SECRET-04) into a false sense of safety,
  which is the difference between a leak that gets rotated and one that does not.
- **Fix:** rewrite to state the actual guarantee and the actual limit, then link the runbook from
  F-SECRET-13. Something like: *"CI runs the same hooks as your local commit. It scans the working
  tree, not git history, so if a secret reaches a commit you must treat it as compromised and follow
  `docs/en/security/leak-response.md` — removing it from a later commit does not un-leak it."*
- **Verification:** the doc claim matches `grep -n "fetch-depth\|gitleaks git" .github/workflows/`.

### F-SECRET-13 — No executable leak-response runbook; no DGII certificate revocation procedure

- **Severity:** High
- **Verified by reading** (`SECURITY.md`, `docs/en/`, `CONTRIBUTING.md`, `docs/en/faq.md`)
- **Where:** `SECURITY.md:31-33` — the entire guidance for an exposed credential is *"Never commit …
  credentials to any repository. Rotate immediately if exposed."*; `docs/en/faq.md:40-45` covers only
  planned expiry rotation. There is no leak-response page in `docs/` (the tree contains `guides/`,
  `reference/`, `examples.md`, `faq.md`, `index.md`, `installation.md`, `python.md`,
  `typescript.md` only).
- **What is missing:** a responder at 3 a.m. has no ordered steps. Specifically absent: (a) **how to
  get a DGII certificate revoked** — for C1 the provider-side fix is a DGII-side action, and no doc
  names it, the RNC account that can perform it, or a contact; (b) the inventory of CI secrets to
  rotate (`DGII_P12_BASE64`, `DGII_P12_PASSWORD`, `DGII_RNC`) and the `gh secret set` commands;
  (c) the **audit step** — enumerating e-CF documents accepted under the leaked certificate during the
  exposure window, which is what determines legal exposure; (d) any history-purge step; (e) an owner
  for each credential and a rotation cadence.
- **Blast radius:** C1, C2, C4. This is not a detection or handling defect — it is the difference
  between a leak that gets rotated at the provider and one that gets "fixed" by deleting a file while
  the attacker keeps issuing tax documents in the holder's name until the certificate expires.
- **Fix:** add `docs/en/security/leak-response.md` (and its `docs/es/` mirror — CI diffs the two file
  lists and `mkdocs build --strict` fails on nav drift) containing the ordered runbook reproduced in
  **Leak-response gap** below, plus a credential register naming an owner, cadence and revocation path
  for C1, C2 and C4. Link it from `SECURITY.md` §"Security guidance" and from `CONTRIBUTING.md`
  §Certificates.
- **Verification:** `test -f docs/en/security/leak-response.md && test -f docs/es/security/leak-response.md`;
  `grep -c 'DGII_P12_BASE64' docs/en/security/leak-response.md` ≥ 1; `mkdocs build --strict` passes.

## Leak-response gap

**Today: a `.p12` leak would be contained poorly and rotated probably not at all.**

Walk the 3 a.m. scenario. A developer realises they committed `DGII_P12_PASSWORD` (or worse, a
base64 `.p12`) yesterday and deleted it this morning. What can they execute from this repo?

| Step | Available? | Evidence |
|---|---|---|
| 1. Detect it | ⚠️ Partially | Only if the file is *still in the tree*. A commit-then-delete is invisible (F-SECRET-04, demonstrated). |
| 2. Contain — revoke at the provider | ❌ **No procedure** | `SECURITY.md:32` says only *"Rotate immediately if exposed."* No DGII revocation path, no contact, no mention that a DGII certificate must be revoked **in DGII**, not just in the repo. |
| 3. Rotate the CI secrets | ❌ **No inventory or steps** | `DGII_P12_BASE64`, `DGII_P12_PASSWORD`, `DGII_RNC` (`integration.yml:32-34`) are referenced but never listed as rotatable items with an owner. No `gh secret set` instructions. |
| 4. Audit what was issued | ❌ **Absent entirely** | Nothing tells the responder to check DGII for e-CF documents issued with the leaked certificate during the exposure window. This is the step that determines legal exposure, and it exists nowhere in the repo. |
| 5. Purge history | ❌ **Not mentioned** | `filter-repo`/BFG appears in no doc. Consistent with a pipeline that never scans history. |
| 6. Close the gap | ❌ | No post-incident step; no "add the pattern to the scanner". |

**The single concrete missing step:** there is no DGII certificate-revocation procedure. For every other
credential in the inventory the provider-side fix is well understood (rotate the npm donor identity,
revoke the DGII status API key, let the bearer token expire). For C1 — the one credential that can
issue legally binding tax documents — `SECURITY.md` and `docs/` never say how to get the certificate
revoked by DGII, who holds the RNC account that can do it, or how to enumerate documents already issued
with it. `docs/en/faq.md:40-45` is the closest thing and it only covers *planned expiry rotation*
("track its expiry … rotate before it lapses"), which is a different problem from a compromise.

Everything else here is well built. The OIDC publish design means the highest-value credentials
(C5, C6) cannot be stolen at all, only misused through repo control — that is the right architecture
and it is why this review is not a failure. What is missing is the one artefact that turns a good
architecture into an operable one.

**Fix — add `docs/en/security/leak-response.md` (mirrored in `docs/es/`, per the CI parity check),
with a runbook ordered by clock-time, not comfort:**

```markdown
# Exposed credential — response order (do NOT stop at step 2)

Clock starts at the COMMIT timestamp, not the discovery timestamp.

1. ROTATE AT THE PROVIDER — this is the fix.
   - .p12 / passphrase (C1/C2): request revocation and reissue of the DGII certificate through the
     DGII account named below, then set new DGII_P12_BASE64 / DGII_P12_PASSWORD repo secrets:
     `gh secret set DGII_P12_BASE64 < new.p12.b64`
   - DGII status API key (C4): rotate in the DGII portal, update DGII_STATUS_API_KEY.
   - DGII bearer token (C3): expires on its own; force re-auth by dropping the cached token.

2. AUDIT THE EXPOSURE WINDOW (commit time → revocation time).
   Pull the DGII submission log for the RNC and list every e-CF accepted in that window. Anything you
   did not send is a forged tax document and is a legal matter, not an engineering one.

3. Replace the value in code with a secret-manager reference; deploy.

4. Purge from git history (`git filter-repo --path <path> --invert-paths`) and tell every contributor
   to re-clone. History and clones still hold it until revoked at step 1 — step 4 alone fixes nothing.

5. Post-incident: why did the gate miss it? Add the pattern to `.gitleaks.toml`; make the secure path
   easier. No blame on the commit — the gate should have caught it.
```

**Credential register** — the owner / TTL / revocation table that `SECURITY.md` should carry, because a
secret nobody can rotate is a secret nobody controls:

| Credential | Owner | Cadence | Revocation path |
|---|---|---|---|
| C1 `.p12` | _(name a human)_ | Cert expiry; alert 60/30/7 d (`SECURITY.md:36`) | DGII revocation + reissue |
| C2 passphrase | same | With every C1 rotation, and on any exposure | Re-export the keystore |
| C4 status API key | _(name a human)_ | 90 days | DGII portal |
| C5/C6 publish | release-please | Per release | Remove the trusted publisher |
